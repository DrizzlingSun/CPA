# Security Advisory: Video Endpoints Allow Any Tenant to Retrieve Other Tenants' Videos via `video_id` (Cross-Tenant IDOR)

> **CVE ID:** Pending assignment（待分配）
> **Status:** Vendor notified on 2026-08-15 — no response received. Unfixed as of 2026-09-30; disclosed to MITRE and published on 2026-09-30. Exploit details intentionally omitted.
> **状态：** 已于 2026-08-15 通知厂商——未获回应。截至 2026-09-30 未修复；2026-09-30 向 MITRE 披露并公开本通告。刻意省略可被直接利用的细节。

## English Version

### Summary

The `GET /openai/v1/videos/:video_id` and `GET /openai/v1/videos/:video_id/content` endpoints resolve upstream credentials through a global map keyed solely by the caller-supplied `video_id` path parameter, without comparing the requesting tenant's api-key against the video's creator. Any authenticated proxy tenant can retrieve videos and metadata generated by another tenant simply by supplying the identifier.

### Affected Product

| Item | Value |
|---|---|
| Product | CLIProxyAPI |
| Vendor | router-for-me (Router-For.ME) — open-source project |
| Vendor homepage | https://github.com/router-for-me/CLIProxyAPI |
| Affected version | v7.2.134 (commit `b8fbe70b`); all earlier versions presumed affected |
| Fixed version | None — unfixed as of 2026-09-30 |
| Affected component | Video handlers (`sdk/api/handlers/openai/openai_videos_handlers.go`), route registration (`internal/api/server_routes.go`) |

### Severity

**CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N — 6.5 (Medium)** *(assessed by the reporters)*

PR:L (rather than N) reflects that the endpoint does require authentication; the flaw is an authenticated tenant-to-tenant IDOR.

CWE-639: Authorization Bypass Through User-Controlled Key (per the original report).

### Prerequisites

- A multi-tenant deployment (two or more `api-keys`) with an upstream xAI credential — the multi-tenant scenario is documented by the project.
- The attacker must hold any valid proxy api-key (their own tenant account, not the victim's) and know or guess the victim's `video_id`. Video identifiers follow a `vid_<base62>` pattern that is not cryptographically random, so enumeration, adjacent-ID inference, and side channels (shared logs, error messages, referer headers) are practical avenues.

### Impact

Any tenant holding a valid proxy api-key can retrieve another tenant's video content, prompts, metadata, status, and the upstream `video_url`. In multi-tenant deployments this is a direct cross-tenant confidentiality violation: generated videos often contain commercially sensitive, personal, or proprietary content. A secondary consequence is metadata disclosure — the prompt, model, and creation timestamp used to generate the video are all returned, revealing the victim's intent or workflow even where the content is not directly accessible.

### Recommended Mitigations (reporter recommendations, pending vendor fix)

- Until a fix is available, avoid running the proxy in multi-tenant mode with mutually distrusting tenants; treat all tenants as one trust domain.
- Upstream: record the creating tenant's principal in the video-to-credential binding and compare it against the authenticated caller on retrieval.

## 中文版本

### 摘要

`GET /openai/v1/videos/:video_id` 与 `GET /openai/v1/videos/:video_id/content` 端点通过一个仅以调用者提供的 `video_id` 路径参数为键的全局映射解析上游凭据，而不将请求租户的 api-key 与视频创建者进行比较。任何已认证的代理租户都可以通过提供标识符来检索另一租户生成的视频和元数据。

### 严重程度

**CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N — 6.5（中等）**（由报告人评定）

采用 PR:L（而非 PR:N）是因为该端点确实需要认证；缺陷属于已认证租户间的 IDOR。

CWE-639：通过用户可控键绕过授权（依据原报告）。

### 前置条件

- 多租户部署（两个及以上 `api-keys`）且配置了上游 xAI 凭据——多租户是项目文档记载的使用场景。
- 攻击者须持有任意有效的代理 api-key（自己的租户账户，而非受害者的），并知道或猜出受害者的 `video_id`。视频标识符遵循 `vid_<base62>` 模式且非加密随机，枚举、相邻 ID 推断和侧信道（共享日志、错误消息、referer 头）均为可行途径。

### 影响

任何持有有效代理 api-key 的租户都可以检索另一租户生成的视频内容、提示词、元数据、状态和上游 `video_url`。在多租户部署中这是直接的跨租户机密性违规：生成的视频通常包含商业敏感、个人或专有内容。次要后果是元数据泄露——用于生成视频的提示词、模型和创建时间戳都会被返回，即使视频内容本身暂时不可直接访问，也可能揭示受害者的意图或工作流程。

### 缓解建议（报告人建议，待厂商官方修复）

- 修复发布前，避免以互不信任的多租户模式运行代理；将所有租户视为同一信任域。
- 上游修复建议：在视频与凭据的绑定中记录创建租户的主体，并在检索时与已认证调用者比对。
